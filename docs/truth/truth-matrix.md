Notes that belong with the rows:
- **S0b, S10, P1:** NOT_FULLY_VERIFIED with no diagnosis. The only item is ipa-healthcheck's `meta.core MetaCheck`
  WARNING "missing /proc/sys/crypto/fips_enabled", which the container kernel causes. ipa-diagnose deliberately
  lists it as undiagnosed rather than calling the server healthy.
- **S4, S7:** with this server's named stopped, ipa-healthcheck does not finish within 120 s. The report is
  UNKNOWN, says plainly that this is not a healthy result, and lists `named.service: inactive` from ipa-diagnose's
  own read-only unit check. No cause is claimed and no fix is offered.
- **S7b:** ipa-healthcheck's certificate checks started the stopped certmonger (upstream ipalib behaviour).
  ipa-diagnose detected and reported this. certmonger could therefore not be observed as stopped.
- **R1 is a miss, not a pass of the product:** with the replica removed but still registered, neither
  ipa-healthcheck nor ipa-diagnose reported the dead peer at capture time. The row passes only because nothing
  false was claimed. There is no live evidence that ipa-diagnose detects a dead replica.
- **R2:** the RUV probe after the lab's removal (`ruv-ldapi-probe-after.txt`) shows only the surviving replica: no
  stale RUV was created, so R2 says nothing about stale-RUV detection.
